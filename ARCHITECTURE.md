# Infinity Render Pipeline — Architecture

This document describes the implementation in this package. Its **Contracts** subsections are normative: they are the invariants each subsystem keeps. When the implementation changes, revise the affected statement. Do not append iteration notes. Principles, design rules, conventions and the work method are in [AGENTS.md](AGENTS.md). Authoring is in [Docs~/Manual/index.md](Docs~/Manual/index.md). Verification state is in [Docs~/Project/Status/FeatureStatus.md](Docs~/Project/Status/FeatureStatus.md). Archived plans and receipts under [Docs~/Record/History/](Docs~/Record/History) are evidence, not a specification.

## 1. System

InfinityRP is a Scriptable Render Pipeline in two layers. `InfinityRenderPipelineBase` (`Runtime/Pipeline/InfinityRenderPipelineBase.cs`, with HDR output ownership in `HDROutputState.cs`) derives from `RenderPipeline` and owns the render context and the frame: global graphics state, `Render`, camera preparation and culling, graph execution, submission, frame transactions and disposal. `InfinityRenderPipeline` (`Runtime/Pipeline/InfinityRenderPipeline.cs`) derives from the base, owns its passes (one instance of each pass class, built at construction) and overrides `RecordCamera`, the base's only hook. A derived pipeline hands the base constructor its `PipelineCapabilities` (`Runtime/Pipeline/Context/`): the features it records, the producers every camera must produce, whether its graph may use the async compute queue, and its mesh pass table with the entry whose members cast shadows. `InfinityRenderPipeline` records every feature with async compute, requires Depth, GBuffer, DeferredShading and Display, and registers the nine passes of `InfinityMeshPasses` (`Runtime/Pipeline/PipelineIDs.cs`); `TestRenderPipeline` (`Tests/Editor/`) records depth and presents it with its own depth and shadow table, a second reader of the base API that is compiled and never instantiated. A camera frame collects Unity culling results, builds an Infinity light context, records a render graph, executes that graph, and submits the scriptable render context.

Two geometry paths share the frame:

- Native renderers are submitted with Unity `CullingResults` and `RendererList`s, shadow lists created from `ShadowDrawingSettings`. Lightmaps, legacy probes, light-probe proxy volumes, shadowmask and motion data stay on those renderer lists. Camera renderer lists are built only by `CameraRendererLists` from `RendererListParams`; the asset's instancing flag sets `DrawingSettings.enableInstancing`; Unity 6000.6 removed dynamic batching from `DrawingSettings`. A renderer list is created after culling only when a live pass consumes it, and submitting a list this graph did not create for the pass throws.
- `MeshComponent` instances are entities of `MeshWorld` and are submitted through `RGMeshDrawListHandle`. A mesh component does not discover or modify a `Renderer`.

The package owns the render graph, the physical resource pool, image history, the mesh world and its GPU entity columns, light records, shadow allocation and the atmosphere profile. Unity owns the device, command submission, fences, native culling and the Volume manager.

Three contexts carry that state, one per clock. `RenderContext` (`Runtime/Pipeline/Context/`) is the pipeline-lifetime root: the resource pool, the scene world, the render graph, the shared atmosphere cache, Adaptive Probe Volumes, the `CameraStateTable` and the pipeline-wide frame transactions, built in that dependency order and disposed in reverse. `FrameContext` holds one `Render` call's engine facts: the scriptable render context, the frame number (`Time.frameCount`, read once) and the shadowmask mode. Capture reads that frame from the `FrameContext` passed to `PipelineDiagnostics.BeforeCamera` and counts a player frame once. The number is not stored on `CameraSetup`. A Game view repaint of the same frame is not another frame. `ViewContext` is one camera's record input, flattened from its `CameraSetup`, its `SceneCullingResults` and the frame context.

### Contracts

- The base, in every file that declares it, and `Runtime/Pipeline/Context/` name neither `InfinityRenderPipeline`, its `InfinityMeshPasses`, nor a pass type; the frame reads only the listed pass-domain types (camera culling, the output transform and its decision, shared shader IDs, screen-space mode, and the camera state's combine-LUT cache, temporal color view and shadow and light-loop constant buffers, §16) (`pipelinebase`).
- The root forwards nothing and no subsystem refers back to it. A pass is a class the pipeline constructs once and never names the pipeline or the root: per-camera facts come from `ViewContext`, services and the passes it calls through its constructor (`passroot`). Nothing keeps a `ScriptableRenderContext` past the `Render` call that received it.
- Hot paths are structs and Burst jobs with an explicit `Allocator` (`Persistent`, `TempJob` or `Temp`), chosen by the last reader as AGENTS R17 orders the classes. `unsafe` is limited to native containers and culling jobs. Burst jobs do not capture managed delegates.
- `MeshDrawCommandKey`, `BufferDescriptor` and `TextureDescriptor` use field-level `Equals`; `GetHashCode` only accelerates lookup. Filter, grouping and sort are three operations, not one hash. Sort keys saturate signed and unsigned 16-bit segments before packing; silent truncation is not saturation.
- Steady state allocates no managed memory inside `Render`: after warmup, with fixed object counts and a fixed feature set, for stationary and moving objects, and for every camera of a frame, Scene and Game views together. Growth, registration, feature toggles and requested diagnostics are outside that path. The measurement counts `GC.Alloc` per `Render` call and reports it per camera type; an allocation inside a Unity Editor API is Editor-only and is listed in §16 with its call stack. A resource the compiled shader variant does not sample is not bound. Reuse does not shorten recording, submission, cancellation or completion ownership.

## 2. Layout

| Path | Assembly | Owns |
|---|---|---|
| `Runtime/` | `Unity.RenderPipelines.Infinity.Runtime` | Pipeline base and the desktop pipeline, passes, mesh and light pipelines, volumes, components |
| `Editor/` | `Unity.RenderPipelines.Infinity.Editor` | Inspectors, menus, Shader Graph target, stripper, validation |
| `Editor/Cli/` | `Unity.RenderPipelines.Infinity.Cli.Editor` | Command adapter, compiled only with `INFINITY_UNITY_CLI` |
| `Runtime/Validation/` | `Unity.RenderPipelines.Infinity.Validation` | Validation scenarios, compiled only for Editor and Development builds |
| `Editor/ShaderGraph/` | Compiled into `Unity.ShaderGraph.Editor` by one asmref | Shader Graph target only. It refers to Infinity by strings |
| `Shaders/` | `Unity.RenderPipelines.Infinity.Shaders` | HLSL, surface shaders, compute shaders |
| `Tests/Editor/` | `Unity.RenderPipelines.Infinity.Tests` | EditMode tests and `TestRenderPipeline` |
| `Tools/` | None | Offline checks, texture-view generation, refresh and capture scripts |

Runtime code is grouped by owner: Core, Scene, Mesh, Terrain, Material, Lighting, Atmosphere, RayTracing, RenderGraph, GPUResource, Volume and Pipeline in the runtime assembly, and the validation scenarios in their own assembly. Dependencies point down: Core holds only neutral types (geometry, device conventions, entity identity, documentation links), GPUResource depends on Core, RenderGraph on GPUResource and Core, material routing (`InfinityTech.Rendering.MaterialPipeline`) on neither, and the mesh mechanism (world, pass caches, backends, culling contexts, draw lists) on those layers but not on the pipeline; mesh shader IDs live in `MeshShaderIDs`. A shader property name has one C# ID: a pass binding lives in its pass `UtilityData`, a name several passes bind lives in `PassShaderIDs`, and camera matrices in the `ViewUniform` record. Material routing notifies mesh components through an event, not a call. `static_check.py` enforces these directions. `Runtime/Pipeline/Pass/` groups the pass classes by domain: Geometry, Lighting, Shadow, ScreenSpace, Volumetric, Translucent, Temporal, Post, Output, Debug. Volume components live in `Runtime/Volume/<domain>/` under `InfinityTech.Rendering.Volume`. The atmosphere profile lives in `Runtime/Atmosphere/` under `InfinityTech.Rendering.Atmosphere` and is not a Volume component. `AtmosphereParameter`, `AtmosphereSharedCache` and `AtmosphereViewCache` live beside it and stay in `InfinityTech.Rendering.Pipeline`. Shaders use `Shaders/Library`, `Shaders/Surface`, `Shaders/Utility`, `Shaders/Mesh`, `Shaders/RayTracing` and `Shaders/Pass` with the same pass domains except Output. A shader's `InfinityPipeline/` name does not follow its file path.

### Scene world

`SceneWorld` (`Runtime/Scene/World/`, namespace `InfinityTech.Rendering.SceneModules`) is the pipeline's derived view of the scene: one module per scene type. The namespace is not `Scene` or `SceneWorld`: inside `InfinityTech.Rendering` those simple names hide `UnityEngine.SceneManagement.Scene` and the `SceneWorld` type. Each module has a persistent layer derived from that type's component registry, a view layer rebuilt per camera and, where it draws, a graph layer reset with each graph.

| Module | Persistent layer | View layer |
|---|---|---|
| `meshes` (`MeshWorld`) | entities, elements, pass caches, GPU columns | the camera's mesh culling context, views and draw lists (§7) |
| `lights` (`LightModule`) | light table by light entity id, cookie atlas, cached local shadow atlas | `LightContext`, rebuilt from the camera's visible lights |
| `probes` (`ProbeModule`) | probe table by `ReflectionProbe` entity id, probe atlas | the probe list `LightContext` resolves |
| `decals` (`DecalModule`) | decal table | the DBuffer feature request |
| `terrains` (`TerrainModule`, in development) | terrain table | per-camera section LOD for a component that has a live sector and TerrainData; no pass draws it yet |

- A component registers itself, once per enable and without a closure, in its type's `ComponentRegistry` (`Runtime/Core/`). That registry is the single authority for which components exist. It lives as long as the process, like the Unity objects it mirrors, and holds no work aimed at any world. Mesh components additionally queue their registration epochs, removals (each naming the world that holds the entity), syncs and static poses on `MeshComponent`; the world that consumes a removal applies it only when it holds the entity.
- A module table is a `SceneTable` (`Runtime/Core/`): a rebuild is staged when its registry's version changed since the published table. `SceneWorld.Update` is one transaction: every table stages, the mesh world applies the structural edits in its own transaction, and only then do the tables publish and advance their revision. A failure rolls every module back and keeps the queued work. A new world rebuilds every module from the registries, so a replaced pipeline loses no light, probe, decal or terrain.
- Lighting and the scene world never name the pipeline; `static_check layering` enforces it.

## 3. Configuration

| Concern | Owner |
|---|---|
| Runtime compute shaders, blit material, BestFit LUT | `InfinityRenderPipelineGlobalSettings` containers with `[ResourcePath]` |
| Default Volume profile | `InfinityDefaultVolumeProfileSettings` on Global Settings |
| Quality Volume profile, render scale, shadows, atmosphere, diffusion profiles, output mode, frame settings, mesh backend | `InfinityRenderPipelineAsset` |
| Per-camera Volume mask and trigger, super-resolution override, frame-setting overrides | `InfinityAdditionalCameraData` |
| Analytic light shape and Infinity-only light fields | `InfinityAdditionalLightData` |
| Physical light color, intensity, temperature, range, spot angles, shadows, cookie, culling mask, rendering-layer mask, bake type | Unity `Light` |
| Feature quality parameters | Volume component, resolved through `QualityPresets` unless the level is Custom |
| Debug view | `InfinityDebugDisplaySettings` at runtime. It is not serialized on the pipeline asset |

The base constructor calls `VolumeManager.Initialize(defaultProfile, qualityProfile)` once. Disposal deinitializes that manager and restores `SupportedRenderingFeatures`, `Shader.globalRenderPipeline` and the `GraphicsSettings` flags captured at construction. A second registration of the same profile is not performed. There is no second hardcoded default profile.

The Editor discovers Volume types by reflection. A Player builds its registry from the components present on the global default profile. Pipeline creation rejects an incomplete registry. Optional features record when `VolumeComponent.IsActive()` is true. `overrideState` marks a scene override. It does not enable a feature.

`EQualityLevel` is Low, Medium, High, Ultra or Custom. `Resolve()` returns a settings struct. Custom reads the Volume parameters. Every other level reads the preset table in `Runtime/Pipeline/Quality/`. Passes consume the struct and do not branch on the quality level.

### Contracts

- Default Volume values come only from `InfinityDefaultVolumeProfileSettings`; quality-level values only from the optional asset `qualityVolumeProfile`. A missing Player component type returns null; no hardcoded value replaces it. The default profile includes the required color and exposure components and every consumed optional type.
- Passes read blended components from the camera's `VolumeSnapshot`, captured once after `VolumeManager.Update`; a component missing from the stack throws there, not in a pass. The atmosphere profile is resolved and validated once per camera into `CameraSetup.atmosphere`.
- Required exposure reads the resolved camera stack; `overrideState` does not gate it. Exposure is a multiply before the LUT. Tonemap is None or ACES. Combine LUT has no inactive-component constant fallback.
- A Volume feature exposes `quality` plus its low-level parameters; `Resolve()` returns `F<Feature>Settings`. Atmosphere, deferred shading and temporal anti-aliasing are not Volume features.
- Runtime resources live only in Global Settings `IRenderPipelineResources` containers with `[ResourcePath]`. The pipeline asset never references runtime shaders; its material fields are optional overrides for objects created from the GameObject menu. A missing required resource fails at record or setup. `ResolveDefaultVolumeProfile` throws when the Global Settings slot is empty. There is no `Resources.Load`. Capture diagnostics shaders live in the optional `InfinityRenderPipelineCaptureShaders` container (pipeline construction requires the other three; Unity does not add a container type to an existing asset, so the Wizard's Global settings Fix adds it explicitly, marked dirty and not saved); `CaptureShadersStripper` removes it from players built without Development, and a capture request then fails while the pipeline runs. Player shader stripping lives in `Editor/Material/`.
- Debug state is runtime and owned by `InfinityDebugDisplaySettings`; `debugView` is not serialized on the pipeline asset. A debugger control exists only with a consumer.
- The pipeline reads its asset only through `InfinityRenderPipelineAsset.Settings`, one snapshot taken at construction and normalized once (clamps, cascade ratios, resolved shadow filter). An Inspector edit recreates the pipeline through `RenderPipelineAsset.OnValidate`. Runtime code never writes the asset; Editor tools edit it through `SerializedProperty`. Static renderer poses refresh once per pipeline instance (in the Editor only when `updateProxy` is set).

## 4. Camera frame

`Render(ScriptableRenderContext, List<Camera>)` is the frame entry; `RenderCamera` runs one camera in four stages. `PrepareCamera` returns a `CameraSetup` holding every decision that does not need culling: render policy, frame settings, dimensions, temporal resolve and history reset, the volume update and its `VolumeSnapshot`, the validated `AtmosphereParameter`, camera uniforms, debug view, output transform, and the requested features with their support context. `CullCamera` runs Unity camera setup and culling, the mesh culling context, the terrain module's view layer, `LightContext.Build` and atlas resolution, and returns `SceneCullingResults`: Unity's culling results, the main mesh culling context, the light module's view layer, the mesh world and the published decal count. The derived pipeline's `RecordCamera(in ViewContext, CommandBuffer)` records its pass list (the desktop list is below) from the `ViewContext` built from the frame context and both stages; the command buffer takes constants uploaded ahead of the graph. The base then runs `EnsureRequiredProducers` with the capabilities' required producers, and the render context's graph executes the recording. `EPipelineProfileId.RecordRG` and `ExecuteRG` are profiler labels around the last two stages.

`FrameFeatureSet.ResolveFrame` runs inside `PrepareCamera` on `FrameFeatureInputs` (the pipeline's required producers, frame settings, temporal resolve, volumes, decal count, the support context with the pipeline's feature mask and RTAO readiness). `ResolveContent` runs after `LightContext.Build` on `ContentFeatureInputs` and decides tile masks, moment shadows, atlas updates and contact shadows from the collected lights. `ViewContext.sceneColor` (`SceneColorKeys`) is then derived from the resolved features: the key of the opaque, fogged, resolved and display scene color.

Recording order, with the gate that skips a step:

1. **Frame constants.** `UploadLightData`, `ComputeLightCookies`, `ComputeReflectionProbes`, `ComputeCombineLuts`, `ComputeAtmosphericLUT`, `ComputeTemporalColorPyramid`. Cookies, probes and the color pyramid record only when their feature is enabled. The atmosphere lookup requires `atmosphericalProfile`.
2. **Geometry.** `MeshOcclusionPass.CullMainViews` returns the camera's `MeshMainViews`. When temporal rendering, Hi-Z, GPU indirect drawing, live instances and a valid Hi-Z history are all present, its depth view tests the previous frame's pyramid; otherwise the depth, recovery and main views are one frustum view. `RasterDepth` creates its list from the depth view. With two stages, `CreateEarlyOccluder` records `ComputeEarlyFurthestHiZ` of that depth, `CullEarlyViews` culls the main view against it and derives the remainder of the depth view from the depth and main views, and `RasterDepthRecovery` creates the remainder depth list. Optional `RasterDBuffer` when the world contains decals, then `RasterGBuffer`, `RasterMotion`; they, forward and the translucent passes create their lists from the main view they receive. Cascade and local shadow cull one light view per slice inside those passes, so the camera's occluder never reaches them. Creating a list declares its producer, and a view's first nonempty GPU list also declares the view's visibility producer. Compile places a list producer after every pass that writes its inputs and at the start of the native group that contains its first consumer, so shadow list producers run immediately before the shadow group, on the graphics queue. A view producer has no raster consumer and goes right after its inputs: a frustum or light view reads no graph-written input, so its producer is placed at the start of the graph and its visibility transient lives until its last list producer; an occluded view's producer follows what writes its inputs: this frame's early Hi-Z for the main view, the transform versions it compares for the history view. The recovery view has no producer; its list producer follows the depth and main view producers whose visibility it reads.
3. **Depth-derived work.** `ComputeHiZ`, `ComputeHalfResDownsample`, `ComputeLightTileMask` when a local light list exists, ray-traced or ground-truth occlusion, `ComputeContactShadow`.
4. **Shadows.** `CullShadowCasterSplits` (the camera's allocated cascade and local splits, sorted by light, in one Unity `CullShadowCasters` call), `RasterCascadeShadow`, `RasterLocalShadow`, `ComputeShadowMoments` when a moment filter is in use.
5. **Lighting.** `ComputeDeferredShading`, optional deferred-lighting capture, `RasterForward`, then screen-space reflection and screen-space indirect diffuse (recorded once on every device, right before the composite that consumes them), `ComputeScreenSpaceComposite` when SSR or SSGI records (otherwise the lighting buffer is the opaque scene color), `CopyHistorySSR`, `CopyHistorySSGI`, `ComputeBurleySubsurface`, `ComputeAtmosphericSkyAndFog`, optional lighting capture.
6. **Translucency.** `RasterTranslucentDepth`, volumetric cloud and its history copy, volumetric fog and its history copy, `ComputeFogComposite` when fog or clouds record (otherwise the opaque scene color is the fogged one), translucent T0, `ComputeColorPyramid`, translucent T1, translucent T2.
7. **Temporal resolve and output.** `ComputeSuperResolution` or `ComputeAntiAliasing` by the camera's `ETemporalResolve`; preview cameras have none. Then `RecordCameraOutput`.

Draw-list release is paired with execution. A camera exception rolls the frame state back, discards unproduced shared reservations, and preserves the first exception. Queue-accepted work is still submitted. Physical retirement runs after a successful submit and a known completion fence.

Async eligibility is a queue assignment. It is not a measurement of overlap. A graph uses the async queue only when the pipeline's capabilities allow it and the device supports it. The current Metal validation host reports no async compute support. Early occlusion recovery and late shading, subsurface, temporal resolve and post stay on the graphics queue because their inputs are the surrounding raster work.

### Contracts

- Compute kernels (index and thread-group size), compute local keywords and blit shader pass indices are resolved once into `PipelineKernels` and `BlitShaderPasses` when `InfinityRenderPipelineResources` loads, and again in the first frame after an Editor import of a shader or compute shader. `FeatureRegistry` evaluates each feature's kernels and textures at that moment; per camera it adds only the pipeline's feature mask and temporal, diffusion-profile and RTAO support. A kernel no feature gates, and every blit pass, is required: resolution throws. Passes read both tables at record time through the `InfinityRenderPipelineResources` they receive, never a stored copy, so a re-resolution reaches every pass.
- Volume, asset and dependency configuration run before culling. Recording that depends on scene content is decided after `LightContext.Build`.
- Every camera requests the pipeline's `PipelineCapabilities.requiredProducers`. Resources that cannot support one fail whenever they resolve, after a shader import included, and the base throws after recording when a camera did not produce one or its temporal resolve. A feature outside `PipelineCapabilities.features` does not record and reports "This pipeline does not record it."; temporal resolve picks super resolution or TAA only when the pipeline records it, and RTAO is ready only in a pipeline that records it. A camera that records motion declares `DepthTextureMode.MotionVectors` once; the pipeline does not rewrite the flag every frame.
- A pass decides whether an optional input exists from the feature set (or the producer's own allocator state, as for shadow moments) and reads it with `QueryTexture`, which throws when the producer did not register it. It never infers a producer from whether a resource happens to be registered; `TryQueryTexture` remains only for debug views and for a translucent stage that adopts the reactive mask an earlier stage created.
- Per-camera inputs reach a pass only through `ViewContext`, taken by `in` and never stored; no pipeline field holds the active camera. A pass reads the frame number, the shadowmask mode and the light context from it, never from `Time`, `QualitySettings` or the scene world.
- Camera matrices live in the `ViewUniform` constant buffer (`Shaders/Library/ViewUniform.hlsl`, GPU-RECORD `ViewUniform`), which declares only constants some shader reads: the matrices, each under the name of its exact variant, the depth parameters (near, far, orthographic, reversed Z) and the current and previous TAA jitter in sampled UV. `CameraFrameState` owns one `UniformBuffer<ViewUniform>` per camera; `CameraUniform.SetUniformData` writes it once before culling and binds it globally, so raster and compute passes, async ones included, read the same values and no pass copies a camera matrix. Compute shaders read the camera position and forward from these matrices (`ViewPositionWS`, `ViewForwardWS`) and the projection kind from the depth parameters (`ViewIsOrthographic`); no pass uploads a camera vector, depth parameter or jitter. Raster shaders read the engine's `_WorldSpaceCameraPos` from `SetupCameraProperties`. The camera's shadow constants (`ShadowUniform`, in `ShadowSampling.hlsl`) and light-loop constants (`LightLoopUniform`, in `Lighting/LightLoopUniform.hlsl`) are two more such records, each a `UniformBuffer<T>` bound under its type name and written once into the camera command buffer at the start of the desktop `RecordCamera`, after `CullCamera` built the lights; resource bindings stay with `ShadowInputs` and `LightLoopInputs`, and no pass sets a shadow or light-loop scalar. The graph joins the async queue at its end, so a later camera's upload never overtakes a reader. Shadow casters project with `_ShadowCasterViewProj`, which the shadow passes set per cascade or local face; they never touch camera constants. The UnifiedRayTracing occlusion shader receives its matrix through the backend's binding calls.
- A missing volume or a disabled optional feature skips recording; so does an optional feature whose kernel is missing, with its reason in the Rendering Debugger. A pass that records trusts the tables: it neither looks a kernel up by name nor checks it again. Lighting, active temporal anti-aliasing and display throw at record when their contract is broken. Execute never contains `if (shader == null) return`.
- History copies of previous-color effects sit after the independent raster window. A graphics transfer immediately after an async producer joins that producer.

## 5. Render graph

`RGBuilder` records passes, textures, buffers and renderer lists for one camera graph. A handle carries the generation of its slot and is valid exactly when that generation is nonzero; every handle-taking accessor resolves through one checked lookup, so a handle from another graph is rejected. Two handles name the same resource when index, type and generation match. Work the core does not model attaches as one `IRGGraphExtension` per builder. The extension sees the recorded passes once per compile and clears its state whenever the recorded graph is dropped, with or without execution. The builder owns it and disposes it after clearing the recorded graph. It does not reorder passes. `DeclareComputePass` and `DeclareTransferPass` record a pass outside the sequence: compile inserts it after the passes that write its inputs and at the start of the native group that contains its first consumer, so the inserted pass does not split that group. A declared pass with no consumer in the recorded sequence (none at all, or only other declared passes) is inserted right after its inputs; without a live consumer it is culled by the same rules as any other pass. Declared passes that share an insertion point are ordered by their read and write edges, and creation order breaks ties. A cycle at that point throws. If an input is written inside or after that group, compile throws. The render graph does not name mesh types; mesh view and draw-list producers are declared passes. A pass stores the extension's ids in `extensionUses`, and pass handles and raster encoders carry their builder's extension, so a draw list from another builder is never consumed or submitted. The render graph depends on neither the pipeline nor the mesh pipeline: it executes on a `ScriptableRenderContext`, and mesh draw lists are its extension, in `Runtime/Mesh/Graph/`. Appended passes keep their recorded order. Declared passes are placed at compile.

Compile places declared passes, then runs structural culling once. Culling propagates across texture and buffer reads. A pass that writes an imported resource, or that calls `EnablePassCulling(false)`, stays live. The compiler then builds native render-pass groups and submission segments. A segment is queued as a unit; a new segment starts at a queue change, a wait, or a create whose physical descriptor matches an allocation released earlier in the open segment, because the pool would hand that allocation over before its last use is queued. A pass-local resource's owner is recorded once per compile. Resource checks compare the handle generation with the live slot and format the API name only when the check fails.

A submission segment is a run of passes on one queue. It breaks when the queue changes, when a pass waits on a cross-queue fence, or when a create (at its group-hoisted position) matches the physical descriptor of an allocation released earlier in the segment. One segment is one `ExecuteCommandBuffer` or `ExecuteCommandBufferAsync`. Adjacent raster passes merge into one native render pass when size, sample count and attachment limits allow and no pass samples an attachment written inside the group. Unity's attachment limit is eight, including depth. A non-imported attachment whose last use is a store becomes `DontCare`. On Metal, an attachment that never leaves that render pass can be memoryless, except a color UAV.

Unity exposes no GPU heap. Overlap is descriptor-level reuse by `ResourcePool`; the graph keeps no slot plan of its own, and both report sizes with the descriptors' one byte estimate. Repeated imports of one physical texture or buffer share one graph identity. Conflicting logical views of one texture fail at record time.

Pass types are fixed by the work. Transfer copies. Raster draws. Compute dispatches. Ray tracing is the render-graph type of the ray-traced occlusion pass. Internally there is one `RGPass<T>`; `EPassType` is set when the pass is added, and `Execute` builds that kind's encoder. The public surface keeps four handles (`RGTransferPassHandle`, `RGComputePassHandle`, `RGRayTracingPassHandle`, `RGRasterPassHandle`) with no shared method bodies: Read, Write, Create and pass culling are one generic extension on `IPassHandle`. Attachments, renderer lists and async compute stay on the handle whose kind can perform them, so a compute handle cannot declare a color attachment. One handle type was rejected because those operations would then be checked only at runtime. Gizmos, wire overlay, final output and UI overlay stay raster. `SetRenderTarget` is not called inside a pass execute. Attachments are declared at record time.

`EnableNativeRenderPass(false)` is used only where a native render-pass attachment cannot represent the target: gizmos and wire overlay, because Unity forbids gizmos inside `BeginRenderPass`; final output, because the backbuffer has no owning `RenderTexture` from which to resolve `AttachmentDescriptor.graphicsFormat`; and UI overlay, because Unity does not expose the overlay renderer list as a native render-pass payload.

`RGBuilder.Execute` propagates the original exception. Graph commands are isolated from the enclosing camera profiler scope. Recording arrays and execution scratch share one arena on the builder. Each element type and length has its own cursor. A cursor advances on every rent of that key and returns to zero when the recorded graph is cleared, after submit. An array is allocated only when one graph rents a key more times than that key has been rented before. Execution scratch continues those cursors, so it does not replace a recording array that is still live. Pass objects return to their pool at that clear. `RGProfilingScope` is a pass range: on one segment the parent sampler begins on the first live pass and ends on the last. A segment split closes it and opens it again. It does not insert a pass. Pass GPU names come from `pass.customSampler`.

### Contracts

- A designed path is not disabled to quiet the Console: no `EnableAsyncCompute(false)` as a correctness switch, no `throw` replaced by `return false`, no dispatch of count 0 that only looks wired. An unimplemented feature is not recorded.
- An invalid `RGTextureHandle` or `RGBufferHandle`, a failed query or a failed resolve fails at record or setup. `Texture2D.blackTexture`, a lighting buffer used as history and an empty `RenderTargetIdentifier` are never bound. Unity's "temporary render texture" message means an empty identifier, not a `GetTemporaryRT` call: check handle validity, pass order and which producer must register the ID.
- Graph textures are created, imported or taken from `ResourcePool`; hot paths do not call `GetTemporaryRT`. Mip chains stay in one compute pass: the graph tracks resources, not subresources.
- Every buffer in the pool, the graph and the caches is a `GraphicsBuffer`; `BufferDescriptor.target` is its `GraphicsBuffer.Target` (default `Structured`; indirect arguments declare `IndirectArguments | Structured`). An external `GraphicsBuffer` import builds its descriptor from the buffer's count, stride and target and lands in the same `RGBuffer.resource` as a pooled one.
- The scoper belongs to the graph builder and clears with the recorded graph. A key names one producer's output for the whole graph: a producer registers only its own fixed key, and nothing moves or republishes a key (R18). A stage whose producer depends on features is read through `ViewContext.sceneColor`, derived with the same conditions those producers record under; consumers do not guess among `LightingBuffer`, `ScreenSpaceCompositeBuffer`, `FoggedSceneColorBuffer`, `AntiAliasingBuffer` and `SuperResolutionBuffer`. With a linear intermediate, the debug view keeps its input under `PreDebugColorBuffer`, writes `DebugViewBuffer`, and `DisplayColorBuffer` is registered once from `sceneColor.display` as the present source.
- Feature code uses `IComputeCommands`, `IRasterCommands`, `IRaytracingCommands` and `ITransferCommands`, implemented by graph encoders. Each encoder keeps its pass type's restrictions and forwards to one `RGCommandCore` that holds the command buffer and the graph's own `RGResourceFactory`; there is no global current factory and no wrapper outside the graph. Graph handles are bound only through an encoder, which resolves them through that factory, so a handle from another graph is rejected where it is bound. `RGTextureHandle` and `RGBufferHandle` have no implicit conversion to a Unity resource, and encoders define no `implicit operator CommandBuffer`. Encoders take shader property IDs, never names, and no `params` overloads; the unified ray-tracing acceleration structure, `SetRayTracingShaderPass` and `DispatchRays` keep a name because Unity has no ID variant. A compute keyword is set through `SetKeyword(ComputeShader, in LocalKeyword, bool)` on the encoder, not on the shader.
- A compute pass's per-graph constants are one GPU-RECORD written at record time with `WriteConstants`, which returns an `RGConstantsHandle`: the record is staged in 16-byte units and copied, when the pass begins and on that pass's queue, into a pass-local pooled constant buffer, which the encoder binds with `SetComputeConstantBufferParam`. The buffer is an ordinary pass-local graph resource, so its lifetime and queue fences are the graph's. A record mirrors its HLSL `cbuffer CBV_<Name>` field for field at the cbuffer packing offsets and fills whole 16-byte registers; the `records` static check compares the offsets. Only values that differ between dispatches of one pass execution are set per dispatch, as loose globals (`RenderGraphConstantsGpuTests` covers the record path).
- `ReadOnlyDepthStencil` is set only when the pass declared read-only depth and does not write it. A color-only target uses the color-only `SetRenderTarget` overload; an empty depth identifier is never put in a `RenderTargetBinding`. Attachment Load is a read. Depth that a later effect or capture consumes is stored.
- A pass is named by its `ProfilingSampler`. `ProfilingSampler.Get` returns null in non-development players, which have no profiler: such a pass records and executes the same without a name, and a null sampler opens and closes no profiling scope.
- `CommandBufferPool.Get()` is unnamed. Camera and pass groups use `ProfilingScope(cmd, sampler)`. A `ProfilingSampler` name never matches a `cmd.BeginSample(string)` argument. In-pass markers use a cached `ProfilingSampler` of that name (`BloomDownsample`, `BloomUpsample`, `MeshViewCulling`, `InitializeIndirectArgs`, `BuildDrawList`). `ProfilingScope(sampler)` without a command buffer is a CPU-only track.
- CPU time has three owners and does not reuse a pass `ProfilingSampler`. The pass sampler, including `CustomSamplerId`, is the GPU and execute name. The pipeline owns `Record.<method>` around each call inside `RecordCamera` and around the base's required-producer check, and `ProcessLight.<stage>` around shadow-cache configuration, cookie resolution, probe resolution, content features and the camera command execution. Lighting owns `Light.<stage>` and `Shadow.<stage>`. Mesh owns `UpdateMeshWorldGPU` and `Mesh.<stage>`. The render graph owns `RG.Compile.<stage>` and `RG.Execute.<stage>`, and those names do not mention a pipeline or a mesh. Each table is `static readonly ProfilerMarker` fields on that layer. `Begin` and `End` do no work in a non-development player, and none of these markers is written into a command buffer.
- RAW, WAR and WAW hazards compile on the effective queue, gated by device async-compute and fence support. An async-queue fence is never queried as a CPU completion signal on a Metal device that does not support it.
- Native submit, queueing the final fence and accepting the frame transaction are three results. A fence that was never queued acknowledges no work.

## 6. Resources and history

`ResourcePool` owns physical textures and buffers for the graph and for other clients; nothing else in GPUResource or RenderGraph allocates GPU memory. Every acquisition returns a handle carrying its lease (acquisition generation), and a return through a handle of an earlier acquisition throws. The pipeline requires graphics fences at construction. `BeginFrame` opens a recording epoch. Release keeps recording references and queued GPU use; the release overloads without a reuse fence rely on that tracking alone. Same-queue reuse follows queue order. Opposite-queue reuse waits on a queued dependency. CPU `SetData` requires no recording or pending use and a CPU-queryable completion, or a separate writable allocation. A CPU frame transition is not permission to write.

Retention watermarks are 400 MiB for textures and 64 MiB for buffers. Resources idle for more than two successful submission epochs are evicted oldest first above those watermarks. The watermarks are not a working-set limit. Destruction waits for a CPU-queryable completion fence and does not block the CPU. Size counters are format estimates, not driver residency.

`HistoryCache` is the only image-history store. It borrows its committed and pending targets from `ResourcePool` and returns replaced or discarded ones with the frame's reuse fence; its owner disposes it before the pool. Readers import the accepted history through `HistoryCache.Read(id, descriptor, resetHistory)`, the one validity rule: same logical layout, committed at least once, not discarded by the camera's reset; a feature that can skip frames also requires its accepted flag. Writers import a pending target with the same descriptor. A producer may write the pending target directly, as temporal anti-aliasing and super resolution do, or copy into it with an explicit CopyHistory transfer. Pending history is accepted only after the camera submission succeeds. A failed camera or a failed frame resets history. Every owner of speculative GPU state is an `IFrameTransaction`: the atmosphere shared cache, local shadow cache, cookie atlas and reflection probe atlas are registered once on the render context; each camera's history cache, atmosphere view cache and combine LUT cache are registered on its `CameraFrameState`. `Render` drives them in one order: `BeginFrame`, `CameraFailed(queueUncertain)` for a throwing camera, `CommitFrame` or `RollbackPending` by the frame's submission, `FlushRetired` with the reuse fence. Each owner states its own camera-failure policy: camera-owned caches discard all pending writes, the shared atmosphere cache drops unproduced pending targets, in-place atlases keep pending state after a queue failure so completion invalidates it, and the local shadow cache relies on commit to invalidate unqueued tiles. Committed and pending acquisitions swap with their descriptors. A failed pending resize does not replace committed history.

Logical width and height are the pixel coordinates and the dispatch bounds. Allocation width and height are the physical compatibility key. `TextureDescriptor.Equals` compares the full logical descriptor. Physical compatibility is a separate field-level compare. History is not rebuilt through `RenderTextureDescriptor`, because that conversion drops the depth-stencil format and the mip count.

Each camera has its own `TextureCapacityState` for internal and display extents. Capacity aligns to 64 texels, grows by at least 12.5% when exceeded, and shrinks after 30 accepted requests whose three-request peak is below 75% of the capacity area. Orientation changes reset that history. Failed submissions do not advance it. A capacity-only change does not invalidate history. Preview and capture cameras do not grow another view. Fixed lookup tables, atlases and external targets use exact allocation.

Screen-texture bindings carry logical and physical metadata. Binding a graph texture to a property in the generated view registry writes that texture's descriptor view, mip-scaled for a mip binding, to the property's `_InfinityView` companion; a graph texture without a logical size is rejected there. A texture outside the graph has no descriptor, so the encoder rejects it for a registered property unless the caller states its view with `TextureView.Whole` or an explicit `TextureView`. Normalized sampling uses `TextureView.hlsl`. Integer loads use logical pixels. Material texture sampling is unchanged. Binding registries are generated with `python3 -B Tools/TextureViews.py --write`.

`MeshWorldGPU.transformVersions` is the exception to image-history ownership. It holds immutable matrix and generation buffers per entity slot. A camera keeps accepted and pending version references. A revision advances only when matrices or slot membership change. Dirty 64-slot pages upload once per version, and a compute producer copies the unchanged elements. Shader motion checks world identity, snapshot range and slot generation.

Clear depth and sampled depth are different values. `ClearRenderTarget` and `AttachmentDescriptor.clearDepth` take `GraphicsConventions.ClearDepthFar`, which is normalized so that 1 means the far plane. Shader comparisons against a sampled depth buffer use `GraphicsConventions.SampledFarDepth`.

### Contracts

- Image history lives only in `HistoryCache`. A same-frame scoper ID that has not been written is not history. Shared-cache validity comes from queue-accepted production, independent of camera success.
- `ReleaseBuffer` and `ReleaseTexture` keep recording references and queued use. Cancelled recordings release only their recording references. Partially queued or uncertain submissions stay protected. Pool return is not proof of safe CPU reuse.
- Camera framebuffer descriptors declare Internal or Display sizing.
- Screen-binding registries are generated only by `python3 -B Tools/TextureViews.py --write`, never by loading assets; the offline gate checks them.

## 7. Mesh drawing pipeline

`MeshComponent` content is not submitted through a renderer list. Layers, from stable to per request:

1. **World**: slot tables for entities, elements, sections and materials, owned by `MeshWorld`, the `meshes` module of the scene world.
2. **Pass**: one `MeshPassCache` per entry of the pipeline's pass table, addressed by `MeshPassId`: which elements belong to the pass and which cached command each draws with.
3. **View**: what a list culls against, the counterpart of Unity's `CullingResults` (R11). `CullMeshView` turns a `MeshViewDesc` (a `MeshCullingContext` of planes, layer, scene and rendering-layer masks and LOD projection; the transform versions its lists bind; an occluder or `MeshOccluder.None`) into an `RGMeshViewHandle`. A view's visibility is evaluated once per entity slot on each side that reads it: on the GPU its producer tests eligibility, LOD, frustum and occluder for every GPU list of the view; on the CPU one job tests eligibility, LOD and frustum for every CPU list of the view. `CullMeshViewRemainder` derives a remainder view from a history view and a current view; it evaluates nothing itself.
4. **Draw list**: one view and one pass, `CreateMeshDrawList(view, pass)`. A list filters its view's visibility and never evaluates it: on the CPU backend a gather job reads each element's entity in the view's CPU visibility, then sort and merge; on the GPU backend one producer kernel reads it in the view's GPU visibility and compacts it.
5. **Graph**: the builder's `MeshGraphExtension` records each nonempty list's producer, and with a view's first nonempty GPU list the view's producer, where the list is created, and submits the list from its raster consumer; its `MeshViewRegistry` holds the graph's views, lists, the views' CPU visibility and the scheduled transform versions.

```text
MeshEntity  (slot = transform slot)  desc, LOD chain, element chain   transforms[], bounds[] parallel columns
  └─ MeshElement (one submesh of one LOD)  section ─► MeshSection (mesh, submesh, refCount)
                                           material ─► MeshMaterial (id, queue, route, stage, shader, refCount)
MeshPassCache   candidates[element] = (entity, command | lod << 24)   commands[] = key (section, material), refCount, stateKey
MeshViewCullingJob  visibility[entity] = 0, or 1 | level << 8 | fade << 16   (one per view, as the MeshViewCulling kernel on the GPU)
MeshDrawListBuild  items (key, command, entity, fade) ─sort─► draws (command, fading, offset, count)
                                                                    + instanceToEntity[] + instanceFade[]
```

Index spaces are entity, element, command, draw and instance; arrays are named `<from>To<to>`. Ids store an index and a generation. Live generations are odd, dead ones even. A killed slot returns to its free list only when the transaction commits, so an id handed out by a rolled-back transaction never matches a later slot.

### World

`MeshWorld.BeginUpdate` opens one transaction and snapshots revisions and dirty pages. Each table logs the slot state before its first change. `Commit` first asks every pass cache to prepare the bindings it would create; a failure leaves the transaction open and the lease's `Dispose` rolls it back. After that the transaction is closed, so nothing can revive a reclaimed slot. Commit then reclaims killed slots, retires sections and materials whose reference count stayed zero, applies pending mobility changes and publishes the dirty elements to every pass cache. `Rollback` replays the logs in reverse, rebuilds the touched section and material lookups and restores revisions and dirty pages.

Poses do not take part in transactions. `WriteEntityPose` writes one static pose; `UpdateDynamicPoses` reads every dynamic entity's `Transform` in an `IJobParallelForTransform`, writes changed poses by entity index and marks dirty pages in a second job. Both throw while a transaction is open. Changing a flag that decides membership (`CastShadow`, `ObjectMotion`), or a layer, rendering or scene mask, is a structural edit. `structuralRevision` is membership plus the layer, rendering and scene masks. It advances in `CreateEntity`, `RemoveEntity`, `SetEntityDesc`, `AddElement`, `SetElementMaterial` and `SetMaterialState`, and rollback restores the snapshot. `transformRevision` is pose and bounds. It advances in `CreateEntity`, `RemoveEntity` and `WriteEntityPose`, and in `UpdateDynamicPoses` when a dynamic pose changes. `ShadowCasterBounds` reads `structuralRevision` for the caster list and both revisions for a stored bounds or local answer. `InfinityRayTracingEnvironment.SyncGeometry` reads both; a different `structuralRevision` clears the acceleration structure and rebuilds every instance. A mask-only edit therefore rebuilds it. Mask edits are cold, and that cost is accepted. `MeshPassCache` keeps its own revision. `MeshWorldGPU` and `MeshTransformVersionCache` read `transformRevision` only. No component polls its transform: a static pose is read when the entity is created, after `NotifyEntityChanged`, and, in the Editor, through `MeshComponentEditNotifier` (Undo-recorded edits of the object or a parent notify that hierarchy; undo, redo and hierarchy changes in Edit mode notify every static component).

### Pass

Membership of an element in a pass is: its material's route and stage enable the pass LightMode (`MaterialRouteUtility.RouteEnablesPass`, the one authority that also sets material pass state), its queue is inside the desc range, and its entity carries the required flags. Pass state on the material is not consulted. A command is keyed by (section slot, material slot) and binds the mesh, material, pass index and submesh range when it is created. Its state key packs a per-cache shader-state rank, the material slot and the section slot, each saturated to its segment. After a shader import `MeshPassShaderUtility.NotifyShadersChanged` advances an epoch and each cache resolves its pass indices again before its next draw list.

The pass table is data of the pipeline (R1): `PipelineCapabilities.meshPasses` reaches `MeshWorld` through `RenderContext` and `SceneWorld`, and the world validates it (unique LightModes, queue ranges inside [0, 5000]) before it allocates anything. A LightMode the material route does not know throws in `MaterialRouteUtility.RouteEnablesPass`. Every pass cache is created with the world, so shadow-caster bounds and residency see them before any draw list; `GetPassCache(MeshPassId)` is an index, and the mesh mechanism names no pass. `PipelineCapabilities.shadowCasterPass` names the entry whose members cast shadows; the light module receives it and `LightContext.Build`, `ShadowAllocator.Allocate` and `ShadowCasterBounds.Collect` take it next to the mesh world. The desktop table is `InfinityMeshPasses`: Depth, GBuffer, Forward, Motion, Shadow, TranslucentDepth, TranslucentT0, T1, T2. Later membership changes upload candidate and command tables in residency. A pass with `requirePreviousTransforms` (Motion and the translucent stages) fails at `CreateMeshDrawList` when its view carries no mesh motion.

### Frame

1. Proxy update: `SceneWorld.Update` consumes the queued registrations and runs one `MeshWorldUpdate` for removals and every dirty component inside the scene transaction, then explicit static poses, then dynamic poses. A component stages its sync inside the transaction and publishes it after the commit; an id is valid only in the world that issued it, and a new world resyncs every registered component. A shader import or a shader swap on a material makes the affected components validate again and the commands resolve their pass indices again.
2. `MeshWorld.UpdateResidency` uploads dirty entity columns, the next transform version and the stale candidate and command tables of each pass cache. The dirty-run list and the column-upload scratch are `Allocator.Temp` locals of that update, and the dynamic-pose jobs use `TempJob` arrays released when they complete. Each transform version keeps its own patch array, grown to its high water, because the version outlives the frame.
3. `MeshWorld.BeginCamera` resets per-camera counters.
4. `InfinityRenderPipeline.RecordCamera` prepares the camera's mesh motion and culls its main views (Camera frame, step 2); the views carry that motion. Each raster pass receives the view it draws as a parameter and creates the list it consumes with `CreateMeshDrawList(view, pass)`, the pass id handed to its constructor; it does not receive a list handle from `RecordCamera`. Shadow passes cull one light view per slice. Creating a list declares its producer; a view's first nonempty GPU list also declares the view's producer, whose kernel the view decides (frustum, occluded or history); a remainder view has none. Compile inserts a list producer after the passes that write its inputs (its view's producer among them) and at the start of the consumer's native group; a view producer has no raster consumer and goes right after its inputs. Culling a view records no pass; the shared transform-version passes stay in recorded order, added by the first list that freezes its tables, which is the depth list before its raster pass is added.
5. Creation freezes the pass cache revision and acquires capacity: a GPU list rents its payload, a CPU list its instance tables. A list with zero pass-cache members, or a list of a remainder view on the CPU backend, is empty: it acquires nothing and records no producer, its raster consumer and renderer list stay live, and submit still rejects a changed revision. A GPU list records one compute producer (`ComputeMeshDrawList`) that reads its view's visibility. The view's first nonempty GPU list records the view's compute producer (`ComputeMeshView`): the view rents its culling-context buffer, retired with the graph and returned behind the submit fence, and creates its visibility, a graph transient of max(1, entity high water) uints, so an empty cascade or a view drawn only on the CPU dispatches nothing. A GPU list of a remainder view reads the visibility of its current view, whose producer it records if no list did, and of its history view, whose list of the same pass recorded that producer; the two must cover the same entity slots, or the list throws. A CPU list records one upload producer (`UploadMeshData`) and schedules its gather, sort and merge jobs at compile when its consumer is live. Every view a live CPU list reads is culled once on the CPU: compile schedules its `MeshViewCullingJob` over every entity slot of the world, which the job reads live and which covers the candidates of every unchanged pass cache, into words of the registry's pool; the gather of every CPU list of the view depends on that job, so a view drawn only on the GPU, or whose CPU lists are empty or culled, evaluates nothing on the CPU. Compile culls a list producer with its consumer and a view producer with its last list producer.
6. Execute: the CPU upload completes the build jobs, its view's culling job among their dependencies, and uploads `instanceToEntity` and `instanceFade`; the CPU consumer issues one `DrawMeshInstancedProcedural` per merged run. The view producer uploads the view's culling context and runs one `MeshViewCulling` kernel (one thread per entity slot) that writes each entity's packed visibility (LOD). The list producer runs `InitializeIndirectArgs` for both ranges of every command slot, then `BuildDrawList` (one thread per element slot) reads the element's entity in that visibility, chooses the range from the element's level and the pass's dither flag, and atomically appends the entity to its command's range. A list of a remainder view runs `BuildDrawListRemainder` instead, which leaves culled every entity its history view saw and otherwise reads its current view's word. The consumer issues one `DrawMeshInstancedIndirect` per live command for its stable range and, for a command with members whose chain has a band, one more for its fading range. Raster submission only draws.
7. `MeshViewRegistry.ReleaseAll`, when the graph is cleared, completes the views' culling jobs and takes their words back by count, completes and frees build jobs, retires list and view payloads, instance buffers and transform-version references, and drops the graph's views. The pool's words are persistent, each grown to the entity high water and the pool to the CPU views of one graph, and are freed when the builder disposes its extension. After native submit, `FlushRetired` returns allocations to `ResourcePool` without clearing outstanding GPU use.

The CPU sorts instances by the pass key, then command, entity and fade, and merges adjacent instances of one command and one fading state. `StateSortKey` puts fading in bit 63 and the command `stateKey` in the low 63 bits, so stable instances precede fading ones and one command stays one run. The command `stateKey` leaves bit 63 clear by saturating its shader rank at 15 bits. The GPU does not read the instance key: it appends instances in candidate-slot order and submits one indirect draw per command in `stateKey` order. `TranslucentColorSortKey` packs priority in the high 16 bits and distance from far to near in the low 32. That key needs strict back-to-front order, which the GPU append does not keep, so `MeshWorld.SelectBackend` records every pass with it (T0, T1 and T2) on the CPU. The order is total.

### LOD

An entity carries a `MeshLODChain` of 1 to 8 levels in `LODGroup` semantics: level *i* draws while the screen size is at least its lower bound `screenSize[i]`, bounds strictly decrease, and below the last bound nothing draws (a last bound of 0 never culls). Screen size is the largest half-extent of the world bounds (`LODGroup.size` / 2 for an unrotated object; rotation grows the world bounds by up to √3) × `scale` × `bias` / distance, where `CameraCulling.LODProjection` takes the camera position, 1 / tan(fov / 2) or 1 / orthographic size, and `QualitySettings.lodBias`; orthographic projections use distance 1. Light contexts copy their camera's projection, so casters switch level with the visible object. Each element names its level.

The cross-fade band of level *i* lies above its bound and is `fadeWidth` × (previous bound − bound) wide, with a previous bound of 1 for level 0; a bound of 0 has no band. Inside the band the fade *f* runs from 0 at the bound to 1 at the band top. Each side of a view packs one word per entity, 0 when culled or `1 | level << 8 | fade << 16`, with 65535 for stable and the band position quantized to [0, 65534): the CPU culling job with `MeshLODSelection.Select` and `Pack`, the GPU culling kernel with `MeshPackLODVisibility` in `MeshLOD.hlsl`. That word is the view's visibility: on the GPU its producer writes `UAV_MeshViewVisibility`, a list reads `SRV_MeshViewVisibility` and a list of a remainder view also reads its history view's words as `SRV_MeshViewDrawn`; on the CPU every gather of the view reads the job's words. A list decodes the word with the pass's dither flag and the element's level (`MeshDrawLod.Range` and `MeshElementRange`). Both sides evaluate the same expression on the same columns; `precise` keeps every view of a context on one answer.

A pass dithers LOD transitions when its queue range is opaque (`MeshPassDesc.ditherLODTransitions`). There, inside a band the selected level draws with +*f* and the next level with −*f* in the command's fading range; `LODDitheringTransition` keeps complementary pixels for the two signs, so the pair covers every pixel once. At *f* = 0 the outgoing level is gone. Translucent passes draw the selected level only and never fade. Every command has a stable and a fading range: GPU command metadata holds index count, start index, base vertex, stable base and fading base (stable base + member count), counts and indirect arguments are interleaved per (command, range), and instance capacity is twice the member count. Fading draws set the global keyword `INFINITY_LOD_DITHER` and clear it afterwards; shaders read the factor through `MeshInstanceFade`. Ray tracing takes level 0 only.

### Content

`MeshComponent` draws a `MeshAsset`: `meshes[i]` is LOD *i* (one mesh may fill several levels), `lODInfos[i].screenSize` its lower bound, `lODInfos[i].materialSlot[s]` the material slot of submesh *s*, and `fadeWidth` the band width. A submesh without a slot entry has no material and draws nothing; an explicit slot outside the asset's materials makes the asset invalid. The asset's materials are authoring defaults that the inspector copies into a component once, on assignment; the component's material array, indexed by slot, is the runtime authority. Components share one geometry state per asset (level meshes, submesh counts, union bounds and the element table, one entry per level and submesh). An edit of the asset or one of its meshes marks that state stale, and every component that references it rebuilds its entity on the next sync. Only a registered component holds a reference on its asset's state, and destroying the asset re-syncs its components. A component whose asset fails `MeshAsset.ThrowIfInvalid` is logged with its context and not drawn.

### Backends and shaders

`EMeshDrawBackendPolicy` is Auto, CPUDirect or GPUIndirect. A diagnostics override wins, then the Rendering Debugger override, then the asset; the pipeline resolves that once per camera into `MeshWorld.requestedBackend` and writes the debugger's backend state. `MeshWorld.SelectBackend` derives each pass's backend from its sort key, the device and that policy (P6): Auto and GPU Indirect use the GPU backend when the device supports compute and instancing, except for a `TranslucentColor` sort key, which always records on the CPU; a missing kernel of the mesh compute shader fails world construction. There is no process-global indirect-argument buffer and no same-frame visible-count readback. The compute shader is required on every backend because transform versions are produced on the GPU.

Visibility is a fact of (view, entity), so it is evaluated once per view on each side that reads it, and the side follows from the readers: a view with a nonempty GPU list evaluates on the GPU, a view with a live CPU list on the CPU, a view with both (the main view under the default policy, whose T0, T1 and T2 record on the CPU) on both. The GPU result is not read back and the CPU result is not uploaded; both derive from the same entity columns and culling context. Pass membership is the list's filter, not part of visibility. Occlusion is an optimization of the GPU side only (P6). A view with a single GPU list (most shadow slices) pays one dispatch more than a fused list kernel; FeatureStatus records it as a measurement item.

Shaders read `InstanceToEntity[SV_InstanceID + InstanceOffset]` through `MeshInstanceEntity`, then `EntityTransforms`, `EntityRenderingLayers` and, for motion, `PreviousEntityTransforms` guarded by generations. A mesh shader declares the SubShader tag `InfinityMeshInstancing = True`; a component whose material lacks it, or lacks a pass its route enables, is logged with its context and not drawn.

`ERenderingLayer : byte` is the shared mesh and light mask, with `Everything = 0xFF`. Surface masks in GBuffer C are an 8-bit unorm value. High bits are rejected.

Recording a view and a list for a pass is:

```csharp
RGMeshViewHandle viewHandle = graph.CullMeshView(new MeshViewDesc(cullingContext, motion, MeshOccluder.None));
RGMeshDrawListHandle drawsHandle = graph.CreateMeshDrawList(viewHandle, m_GBufferMeshPass);
passData.meshDrawListHandle = passHandle.UseMeshDrawList(drawsHandle);
// execute:
cmdEncoder.SubmitMeshDrawList(passData.meshDrawListHandle);
```

`CullMeshView`, `CullMeshViewRemainder` and `CreateMeshDrawList` are internal; content code mutates `MeshComponent` and does not record views or lists. Submitting a mesh draw list records its draw calls into the raster encoder. Native submit and a submission segment are command-buffer submission.

Draw markers are `Shadows.DrawMeshDirect` and `Shadows.DrawMeshIndirect` for the Shadow pass and `RenderLoop.DrawMeshDirect` and `RenderLoop.DrawMeshIndirect` for every other pass. `MeshDrawProfiling` owns the shared samplers. CPU schedule, completion, upload and draw markers include the pass in their name. Completion time can include main-thread job execution. `viewProductions` counts recorded GPU view producers (one kernel each), `drawListProductions` list producers, `drawListKernelDispatches` their kernels and `viewCullingJobs` the CPU view culling jobs (`Mesh.ScheduleViewCulling`) for the last camera, while a frame-tree export counts actual ready dispatches per view producer (`meshViews`) and per list and kernel (`meshDrawLists`). A producer is not recorded inside its consumer's profiling range, so a raster pass group contains that pass's draws. Shared sampler names do not merge graph nodes.

`TranslucentPass` draws MeshComponent content from the TranslucentDepth and T0/T1/T2 passes of the main view before the native renderer list of the same pass, with the pass's keywords and global inputs already bound. TranslucentDepth uses the state key. T0, T1 and T2 record on the CPU and order by priority, then distance from far to near. The two lists are sorted separately, so MeshComponent and native translucent renderers have no distance order between them. Out of scope for this pipeline: GPU sorting of draw keys, meshlets, and replacing renderer lists for Unity `MeshRenderer` objects.

### Contracts

- Entity data belongs to the entity: one logical object owns one entity slot, which is its transform and bounds record; submesh, material and pass add element and command references. An element is one submesh of one LOD level with one material.
- Stable structure is cached; view results are regenerated. Pass caches change incrementally at commit; visibility and LOD are per view on each side that reads the view; sort and compaction are per draw list. There is no `MeshDrawRequest` type. Naming follows Unity's `Cull` → `CullingResults` → `CreateRendererList` chain: `MeshViewDesc` → `CullMeshView` → `RGMeshViewHandle` → `CreateMeshDrawList` / `UseMeshDrawList` / `SubmitMeshDrawList`; a list holds `MeshDrawCall`s merged from `MeshDrawInstance`s of cached `MeshDrawCommand`s.
- A structural lease carries the transaction generation. Section and material reclaim waits for commit. Pass caches live as long as their world. Rollback never truncates free lists. `MeshWorldGPU.Update` throws while a transaction is open; replacement tables are published atomically and draw lists bind the frozen tables.
- Visibility is a pure function of (view, entity). On the GPU one producer per view evaluates it once into a graph transient whose last reader is the view's last list producer; on the CPU one job per view evaluates it once into pooled words whose last reader is the view's last gather. A list only filters it. No visibility result outlives its graph. TempJob arrays do not survive the frame.
- A view's identity is its handle, not its fields: two views with equal descriptors are two views, and a list means what its view and pass say whatever was recorded before it (R18). Views, lists and the scheduled transform versions belong to the builder's `MeshViewRegistry`; `ClearRecordedGraph` releases them and advances the generation, so a handle of another builder or an earlier graph throws.
- A view holds at most one list per pass; a second throws. An occluder belongs to its view. A history occluder (the previous frame's pyramid, which proves nothing for an entity whose transform changed) needs the view's accepted transform version. `CullMeshViewRemainder` takes a history view and a current view of the same culling context (compared as GPU-record bytes) and motion, culled against a newer occluder; a history view has one remainder view. The remainder view is derived: it has no producer and no visibility, and its lists draw the current view's visibility where the history view saw nothing, which is what culling the remainder against the current occluder would give. A list of the remainder view needs the list of the same pass on the history view, which drew those entities. So an instance draws at most once per view and pass in a frame. A frustum view or a view tested against this frame's depth has no remainder. The CPU backend tests no occluder, so a list of a remainder view is empty there. Light views (cascades, local faces) never see a camera occluder: the shadow passes cull them from a `MeshViewDesc` with `MeshOccluder.None`, which `static_check meshpasses` enforces.
- GPU view and list payload objects are empty between uses; physical buffers belong to `ResourcePool`. A payload lifetime is not permission to destroy a buffer or write it from the CPU. Capacity (member count, command high water) is acquired once before recording; execution checks it and never grows or recreates a buffer bound to a live command buffer. A draw list whose pass cache changed after record fails at execute. The stable and fading instance and argument ranges of every command are disjoint.
- CPU direct records no GPU mesh production. Backends hold no static mutable state. The candidate table holds elements of live entities only; neither backend tests an entity generation. A translucent instance's distance is measured from its context's LOD origin.
- `ERenderingLayer` is `enum : byte`, `[Flags]`, `Everything = 0xFF`; no integer layer index is reintroduced. Pass membership does not apply the mask; shadow views do, through visibility.
- Callers use `MeshAsset`, `Mobility`, the instance properties and `SetMaterials`; `Materials` is read-only. One structural transaction per frame syncs every dirty component.
- Notifications: `NotifyGeometryChanged(Mesh)` after in-place mesh edits, `NotifyGeometryChanged(MeshAsset)` after script edits of an asset, `MaterialRouteUtility.ApplyPassState` after route or stage edits, `NotifyMaterialRoutingChanged` after direct queue edits, `NotifyEntityChanged` after static pose, layer, scene or external entity edits from script. Editor edits notify through Undo and hierarchy events. Dynamic poses are read every frame. Ordinary uniforms do not invalidate draw structure. Inspector and Undo callbacks notify without saving assets.
- Every opaque mesh pass (Shadow, Depth, GBuffer, Forward, Motion) declares `multi_compile _ INFINITY_LOD_DITHER` and calls `LODDitheringTransition`.
- Mesh producer markers are `ComputeMeshView` (in-pass scope `MeshViewCulling`), `ComputeMeshDrawList` and `UploadMeshData`. A list producer's in-pass scope is its pass token (`Depth`, `GBuffer`, `Motion`, `Forward`, `Shadow` or a translucent stage), then `InitializeIndirectArgs` and `BuildDrawList` (the scope of `BuildDrawList` and `BuildDrawListRemainder`) on the GPU. Renderer-list submission adds no wrapper. Native `(RP ...)` labels stay as Unity emits them.

## 8. Materials

`_SurfaceRoute` is Deferred (0) or Forward (1). `_TranslucentStage` is None (0), T0 (1), T1 (2) or T2 (3). `MaterialRouteUtility.Read` rejects fractional, non-finite and out-of-range values. Subsurface requires opaque Deferred routing. `ApplyPassState` is the operation that writes renderer pass enables after a route or stage change. `ShaderGUI.ValidateMaterial` does not write serialized state.

GBuffer layout and YCoCg checkerboard encoding live in `Shaders/Library/GBufferPack.hlsl`. `GBufferPass` allocates three `R8G8B8A8_UNorm` targets and a `R16G16B16A16_SFloat` lighting target. InfinityLit exposes base color, normal, roughness, reflectance, specular level, emission color, subsurface profile and thickness, refraction, iridescence and pixel depth offset. It does not expose metallic, mask, occlusion, detail, height or emission textures. Shader Graph Lit has a Metallic block; the runtime lit constant buffer uses reflectance.

Surface shaders are `InfinityPipeline/InfinityLit`, `InfinityLit-Instanced`, `InfinityUnlit`, `InfinityDecal` and `TerrainLit`.

### Contracts

- `MaterialRouteUtility` is the only route and stage parser; there is no second parser or rounding path. Exact values are validated before derived mutations. Runtime edits of `_SurfaceRoute` or `_TranslucentStage` call `ApplyPassState`. An inspector redraw does not apply derived pass state or mark every referencing `MeshComponent` dirty.
- Metal value and out helpers initialize their results before guarded work and return once where the cross-compiler requires a single exit. Resource access stays behind its validity gate. A rejected surface keeps its raw depth. Ray loops exit through an explicit found state and `break` without changing traversal order. Diagnostics are not suppressed and a callee result is not replaced with a caller-side default. Kernel bounds exits and group-barrier participation keep their meaning.
- A degenerate normalization is guarded before a reciprocal length. Required resources are bound and physical inputs validated at setup; no fallback texture substitutes. Compute passes take kernel index and thread-group size from `PipelineKernels` and derive dispatch group counts from that size. Deferred shading uses an 8×8 group; the clustered light lookup keeps 16×16 tiles.
- Shader warning acceptance is public `ShaderUtil` diagnostics after a production dispatch or draw, a fresh log window and the current Example feature chain. A fixture, a reimport or `FindKernel` alone is not that acceptance.

## 9. Lights

`LightSourceShape` stores the analytic emitter: `EInfinityLightType` (Directional, Point, Spot, Rect, Disk), `ESpotShape` (Cone, Pyramid, Box), source radius, soft source radius, source length, source width and height, barn doors, source angle, soft source angle, pyramid aspect and box size. When `InfinityAdditionalLightData` has authored the shape, that struct is authoritative and `LightShapeUtility.ApplyToUnityLight` writes the derived native fields on edits and setters only. A light with no authored shape derives `LightSourceShape` from the native `Light`. The native area size, sun angle and bake type exist only in the Editor, where the lightmapper reads them, so a player has only `type` and `shapeRadius`: `LightShapeBuildProcessor` freezes the Editor-derived shape of every light in each scene a player build processes into its `InfinityAdditionalLightData`, adding one with no distance fade (identical to a light without the component) where none exists, and changes only the built copy. A light that reaches a player unauthored by any other route (a prefab spawned at run time, a light created by script without `SetShape`) renders its type's default extent. The GPU record `LightRecord` has no shape enum. Shape is a combination of parameters and `LightRecordFlags`.

`LightShapes.hlsl` evaluates specular with the representative-point construction and energy normalization, so a large emitter converges to the punctual result at distance. Sphere and disk diffuse use the horizon-clipped form factor. Lines and tubes use line irradiance. Rectangles use a polygon form factor. There is no LTC table. The two soft extents stay in the Infinity light record. Specular normalization and PCSS use them in addition to the emitter extent. Unity's native shape carrier and the lightmapper use the physical extent.

`LightContext.Build` runs per camera after culling. It collects visible lights, computes a conservative screen-tile rectangle on the CPU, sorts local lights by view depth, and builds 128 logarithmic depth bins. `ComputeLightTileMask` writes one 32-bit mask word per 16×16 tile per 32 lights. `LightLoop.hlsl` (`BeginLightLoop`, `NextLight`) is the only loop. Consumers are deferred shading, forward shading, volumetric fog, volumetric clouds, contact shadows and the lighting debug view. Tiles are not culled by opaque depth, so translucent surfaces and volumes share the list. The local-light list rejects a count above `0xFFFF`.

Cookies and IES profiles share one atlas. Reflection probes are prefiltered into one atlas, axis-aligned, and limited to the asset slot count. Each atlas keeps one upload array, grown to its high water, and one queue observer created with the pass that uploads it. Further probes are skipped in priority order. Unity culls probes by their box, so a sphere influence larger than the box can be culled while still visible. Probe rendering layers are not supported. Translucent T0 has no specular environment term.

`LightRecordPack.TryPack` reads the culled transform, final color (linear color, color temperature and intensity), range and spot angle from the `VisibleLight` snapshot, and only fields `VisibleLight` lacks (inner angle, shadow strength, shadow type, baking output) from the `Light`.

`LightRecord` and its HLSL struct are compared by `Tools/StaticCheck/static_check.py` and by an EditMode test. Every `// GPU-RECORD` struct also has its sequential HLSL byte size, with no constant-buffer register padding, in `Tests/Editor/GpuRecordLayout.generated.cs`. The static check rejects a stale copy of that file, and an EditMode test asserts `UnsafeUtility.SizeOf` equals the listed size. Register packing stays in the records check. A C# struct uploaded to a shader carries `// GPU-RECORD: <HlslStruct> <hlsl file>`.

### Contracts

- Unity `Light` owns color, intensity, temperature, range, spot angles, shadow mode, strength, bias, near plane, culling mask, rendering layers, bake type, bounce intensity and the cookie. `InfinityAdditionalLightData` owns `LightSourceShape` and the Infinity-only fields: shadow filter, update mode, contact shadow, volumetric weights, IES, distance fade and light layer. Derived native fields (`type`, `shapeRadius`, and in the Editor `areaSize` and `shadowAngle`) are written on user edits and API setters, never on load. Each visible light's `InfinityAdditionalLightData` is read once per camera from the light module's table into `LightContext.AdditionalData`, and each visible probe's `InfinityAdditionalReflectionProbeData` from the probe module's table; record packing, cookies, probes and shadow caching read them there and never call `TryGetComponent`.
- Atmosphere and light-list outputs are consumer inputs; producers do not prebind them as globals. Every light-list consumer declares the z-bin and tile-mask buffers and binds them with `LightLoopInputs`; the counts and tile parameters are the camera's `LightLoopUniform`. The cookie atlas and the reflection probe atlas are declared and sampled only under `INFINITY_LIGHT_COOKIES` and `INFINITY_REFLECTION_PROBES`; `LightLoopInputs` sets each keyword from whether the camera produced the atlas and binds the atlas only then, so no stand-in texture exists, and every shader pass that reads an atlas compiles both variants (the shader stripper keeps them, because cameras enable cookies and probes through frame settings). Light-context uploads are Transfer producers. Replaced light-context buffers retire after submit.

## 10. Shadows

Cascade shadows use four splits in a 2×2 atlas. The asset owns resolution, split ratios, blend width and shadow distance. Local shadows use an atlas whose tile is `localShadowMapResolution / 4`. The default budget is 16 tiles. A spot, rectangle or disk uses one tile. A point, sphere, line or tube uses six cube faces. Candidates are scored by strength over distance, with single-tile shapes preferred on ties. A candidate that does not fit is dropped, and a later, smaller one may still fit. Rectangle and disk tiles cover a 120° cone in front of the emitter. Receivers outside that cone are unshadowed.

`EShadowFilter` is Hard, PCF, PCSS, VSM or EVSM, per light. `InfinityRenderPipelineAsset.Settings.shadowFilter` holds the quality preset or the custom filter settings. VSM and EVSM build a half-resolution moment atlas for the slices that use them. The keywords `INFINITY_CASCADE_SHADOW_MOMENTS` and `INFINITY_LOCAL_SHADOW_MOMENTS` compile that sample only when the camera produced the atlas, and the pass binds that atlas.

`EShadowUpdateMode` is EveryFrame, OnEnable or OnDemand. Directional lights update every frame. Cached local shadows keep the casters of their last render. Moving casters do not update those tiles, and there is no dynamic-caster overlay. `RequestShadowMapRendering` advances an OnDemand version.

Contact shadows trace the sun as one long ray and up to 24 local lights, largest on screen first, as short rays. Other directional lights are not included. The Volume owns the step counts. Volumetrics do not consume contact shadows.

Mixed lighting supports baked indirect and shadowmask. Distance shadowmask is the Quality shadowmask mode. Subtractive mixed lighting is not supported. Visible `Light.bakingOutput` decides shadowmask for native lights. Mesh state is not that authority.

### Contracts

- Cached depth-atlas tile copies stay raster: Unity `CopyTexture` forbids a partial depth-only copy.
- `ShadowCasterBounds` addresses a slot by light id and scene mask. A slot that was not queried for more than one frame is dropped. The live slot count stays within the queried lights times the scene masks used. A hit still requires the structural revision, the transform revision, and the light's own masks and pose.

## 11. Screen-space shading and subsurface

Screen-space reflection may trace at half resolution. Classify, resolve, temporal filter, bilateral cleanup and history stay at full resolution. History is the temporal output. `Samples` traces 1 to 4 rays inside `SSRTrace`. Each ray writes a Halcyon sample record: unweighted radiance, hit confidence, `Dir * HitT` and a signed inverse pdf. A positive inverse pdf is a hit, zero is empty, and a negative inverse pdf is a miss whose xyz is the unit direction. Facing failure, an edge fade of zero and invalid hit color are empty, so they do not add estimator weight. Resolve rebuilds the hit as that sample's origin plus `Dir * HitT` and rejects a direction into the receiver. It does not sample color and does not weight hits by the GGX pdf. The center pixel uses every hit. Neighbor reuse is a Poisson disk and reads only sample 0. A miss does not enter the average. The blend weight is the mean screen-edge fade of the hits, and the stored color is that average times the fade. Resolve also stores the mean and standard deviation of the unpremultiplied hit colors. Temporal weights the surface-motion and hit-point reprojections by `exp2(-10 * luma(dist))` on the unpremultiplied color and clamps that color to its interval. A history sample whose confidence is below half the current resolve is not reused, and a kept history is not clamped below this frame's color. The stored result is that color times this frame's edge fade. Bilateral cleanup filters color only and keeps the center edge fade. It runs after that only where the hysteresis-smoothed reconstruction variance is high. Classify writes a skip tile's records to zero. The indirect counter is cleared by `SSRClearArgs` in the same shader. Hi-Z and linear tiles share one indirect dispatch; the tile class selects the march. `SSRTRayCast.hlsl` clips each ray to the near and far planes and the screen. Hi-Z walks the closest and furthest pyramids. A hit is the ray segment crossing that raw-depth interval. A full-resolution texel is a point depth. A step that is already behind the next texel still hits when the shared edge lies between the two depths and either neighboring triple is colinear within 0.25 of that step. `SCREEN_TRACE_RELATIVE_THICKNESS` selects 2% of eye depth instead; production shaders do not declare it. There is no Volume thickness. Rough tiles march in screen space and refine a crossing with binary search. The refined segment must still cross the texel it lands on, and the hit stores that texel's depth. Trace-behind and toward-camera are bits of one uniform. Trace samples the accepted unsharpened previous frame through `TemporalColorSource`. That frame already contains the composite, so a later frame can show another bounce. A miss falls back to the probe and sky term. An empty sample does not.

Screen-space indirect diffuse has no resolve kernel and no ray-reuse controls. The work grid is always half resolution. `Samples` averages 1 to 4 cosine rays per work pixel. Those rays sample full-resolution accepted previous color. The production march is the same Hi-Z walk. Defining `SSGI_TRACE_LINEAR` selects the 2D march, with step count `HiZSteps * 4` and four binary-search iterations. An 8×8 group compacts valid pixels in group shared memory and the valid lanes trace in that same dispatch. Denoising then runs two stages. Each stage accumulates temporally and then filters on the tangent plane. The first pass has a 6 m base radius and no normal weight. The second has a 3 m base radius and `saturate(dot)`. The radius is also scaled by view depth, a 3×3 variance of the temporal output, and ambient occlusion when that buffer exists (the local keyword `SSGI_AMBIENT_OCCLUSION` declares and reads it; `SSGIPass` binds it only then). Each stage writes its own history, which is `lerp(filtered, temporal, 0.5 * accumSpeed)` with `accumSpeed` 0.93 when the history is mature. Bilateral upsample always writes full resolution from the second mix. Surface metadata is `R32G32_UInt`: exact depth bits, a 12+12 octahedral normal, 7 bits of age and 1 validity bit. Invalid or off-screen history has zero weight. Half-resolution samples keep the accepted view's quad phase with the history transaction, and reconstruction uses the representative sample positions, including the shorter last interval on an odd edge. Metadata is read with integer loads only, and all lanes take part in the group barriers of the fused trace. The world-space filter radius is `baseRadius * F(viewZ) * F(variance) * F(AO)`; the three functions are monotone stand-ins because the Metro slide does not give their bodies. The production kernels do not write a ray record: ray-hit storage is diagnostic-only, a trace capture snapshots trace radiance before the first temporal stage, and diagnostic readback decodes metadata on the GPU because Metal does not expose `R32G32_UInt` to `AsyncGPUReadback`. Intensity is a Volume scale from 0 to 10. Low and Medium trace one ray. High and Ultra trace two.

Ground-truth ambient occlusion traces, filters and accumulates at half resolution, then upsamples. Its history is half resolution. Ray-traced ambient occlusion records at the internal resolution when Unified Ray Tracing has a context, an acceleration structure, `VisibilityRTAO.urtshader` and at least one instance. Otherwise ground-truth ambient occlusion owns the ambient-occlusion buffer. Ray-traced ambient occlusion does not use the occlusion history cache. `SystemInfo.supportsRayTracing` is not treated as a Metal capability. Metal uses the compute backend of Unified Ray Tracing.

Subsurface scattering, when the Volume is active and a diffusion profile exists, writes a diffuse-only component from deferred and opaque forward shading; the attachment exists only when the device supports it and the frame requests it. Indirect composition replaces that component's indirect term. `ComputeBurleySubsurface` filters the half-resolution diffuse buffer and recomposes full resolution as the original color minus the original diffuse plus the filtered diffuse. Specular and emissive light stay outside the filter. The material profile index selects the diffusion parameters. The Volume owns enable and sample count. The pipeline asset owns the diffusion profile list. No subsurface target is allocated when the feature is off.

### Contracts

- Screen-space reflection `Samples` is rays per pixel, 1 to 4; `ResolveSamples` is the Poisson reuse count, not a ray count. There is no world-space ray length. Hit color is the accepted unsharpened previous frame. `SCREEN_TRACE_RELATIVE_THICKNESS` and `SSGI_TRACE_LINEAR` are diagnostic variants. Bilateral reflection cleanup uses hysteresis 0.5 on the reconstruction variance.
- Subsurface routing requires opaque Deferred subsurface materials.
- Ray-traced occlusion selects `ComputeRayTracedOcclusion` or `RayTracingOcclusion` from its Unified Ray Tracing backend; its graph pass type stays RayTracing.

## 12. Atmosphere, fog, clouds and translucency

`AtmosphericalProfile` on the pipeline asset is the only atmosphere configuration. `AtmosphereParameter.FromProfile(null)` throws. `ThrowIfInvalid` rejects out-of-range thickness, scattering, heights, ozone and sun angle. Lengths are meters. Scattering and absorption are stored per kilometer and multiplied by `ScatterPerKmToPerMeter` (0.001) at bind. Volume does not override the atmosphere, and there is no `AtmosphereParameter.Default()`. The atmosphere's sun is the camera's sun record; a camera without a directional light has no sun, its sun radiance is zero and the sky and its irradiance are black.

Lookup tables and the aerial-perspective volume are compute products. Cubemap faces are a `RWTexture2DArray`. Sky and fog are applied in `ComputeAtmosphericSkyAndFog` after opaque lighting and before translucent depth.

Volumetric fog and volumetric clouds record when their frame setting is on, the Volume component is active, and their kernels exist. Fog builds an 8×8-pixel froxel volume and reads the light loop. Clouds trace at half internal resolution, require the atmosphere transmittance table, and read the light loop and shadow inputs. Each keeps its own history.

Translucent depth is followed by clouds, fog, fog composite, T0, the color pyramid, T1 and T2. T1 is the refraction stage and reads the pyramid. T0 is lit before that pyramid. T2 is the last translucent stage and includes unlit and overlay-canvas geometry that is not the screen-space overlay list.

### Contracts

- The atmosphere compute shader uses one unit system, meters with scattering converted at bind; not both. Atmosphere tables are not produced with `Blit`, `SetRenderTarget` or `BuiltinRenderTextureType`.
- The per-camera view cache (sky-view table, aerial-perspective volume, sun buffer) keys on the atmosphere parameters, the sun direction and illuminance, the camera position quantized to 1 m and the exact unjittered view direction and projection. The aerial-perspective volume is aligned to the frustum, so turning in place regenerates it.
- Atlases that live across cameras and frames follow `AtmosphereSharedCache`: pending reservations, commit on queue-accepted `MarkProduced`, `DiscardUnproducedPending` for failed cameras, physical retirement after submit. Cross-frame keys are instance IDs, not per-frame record indices.

## 13. Temporal resolve and output

`UNITY_MATRIX_VP` is `Matrix_ViewJitterProj`. Depth and GBuffer are rasterized in jittered clip space. Reconstruction from a depth buffer uses the jittered inverse view-projection. `FlipY` in this package means `GL.GetGPUProjectionMatrix` with `renderIntoTexture = false`. Motion vectors use the jittered position for coverage and the unjittered clip positions for velocity.

Temporal anti-aliasing reads the current frame at the texel center with point sampling. It does not bilinear-sample at `uv - jitter`. Color history is reprojected by motion. Depth history is reprojected by motion plus the change in jitter. Neighborhood clipping uses reversible luminance compression. Sharpening scales RGB together. The sharpen constant in `Compute_TemporalAntiAliasing.compute` is 0.35. One 8×8 dispatch with a one-pixel halo writes unsharpened `RGBA16F` color and sample age, and `R32` surface depth, to pending history. Sharpened color is display-only. Halo lanes participate in the group barrier.

Super resolution writes unsharpened `RGBA16F` color and display-grid `R32` depth to pending history in the same dispatch as the display color. Its sharpen constant is 0.5. The display result is not copied into history. Reset and off-screen history are not sampled.

`renderScale` is in `[0.5, 1]` and applies to Game cameras when super resolution is enabled. One per-camera descriptor owns internal and display size. Dimensions freeze after `BeginCameraRendering`.

`PrepareCamera` writes the camera's `ETemporalResolve` (None, TAA or SuperResolution) once, from its render policy and dimensions; feature requests, the resolve dispatch and the required-producer check all read it. `CameraFrameState.ResolveHistoryReset` is the only writer of `EHistoryReset`, in this priority: a non-temporal camera (preview, probe face), a capture or validation lock (Editor and Development builds), no committed frame, a game camera that skipped a frame, a rolled-back previous frame, changed dimensions, a cut or projection change. Passes read `resetsHistory` from `ViewContext`. Scene view uses the full pipeline; a gap in the global frame counter does not reset a live Scene view. Reset frames use zero jitter. Game cameras recycle history after a frame gap greater than one.

`OutputPlan` chooses a direct camera target or a display-linear intermediate before post-processing. `PostCombine.hlsl` is the only grading, exposure, bloom, vignette and grain implementation. When no linear consumer exists, that draw also encodes and writes the imported camera target. Hardware-sRGB UI then blends on that target. HDR UI, a debug view, Editor overlays and a requested linear capture keep `DisplayColorBuffer`. A later draw encodes it. Encoded targets are never published as linear buffers. Debug view runs after post processing and before the Editor overlays, only when a debug view is active, and writes a linear quantity into its own target (§5); it is not a second encoder. One table indexed by `EDebugView` (`DebugViewPassUtilityData`) gives each view its `EDebugViewKernel` and the graph keys of its optional input; the kernel is also the bind set. The first registered key is read, and a view whose input is absent (or a probe atlas view with no probe) uses the Missing kernel. `DebugViewPass` and the `PipelineKernels.debugView` kernels exist only in Editor and Development builds, as does the call; `EDebugView` and the debug settings stay in every build.

`ImportBackbuffer` brings the camera target into the graph. An imported resource is not created or released by the pool. Player cameras that target a display resolve sRGB from `Display.requiresSrgbBlitToBackbuffer` when no render-texture format is known. HDR reads the active swapchain format, gamut and paper white. Linear Rec.2020, PQ Rec.2020 and linear Rec.709 scRGB are separate encodings. HLG is not available through Unity's color-gamut API. While HDR output is active the pipeline owns automatic tonemapping and restores it on exit.

Screen-space overlay UI records for a Game camera with no target texture, with `CreateUIOverlayRendererList` and `DrawRendererList`; it is not `DrawUIOverlay`. On the linear-intermediate path it draws into `DisplayColorBuffer` before encoding. On the direct path it draws into the hardware-sRGB target. Scene view does not draw that list. Screen-space camera and world-space canvases use the T2 renderer list.

`ReactiveMask` is an R8 attachment allocated only for temporal anti-aliasing. The first translucent color pass clears it even when it draws nothing. Later passes load it. Other temporal policies omit the attachment.

### Contracts

- On the compute side the jittered reconstruction matrix is `Matrix_*FlipYJitter*`. Motion vectors are jitter-free; `SV_POSITION` uses the jittered view-projection, the clip positions used for velocity do not.
- Color history uses `uv - motion`. Raster depth history uses `uv - motion + previousJitterUV - currentJitterUV`. Motion metadata carries expected previous raw depth, current surface raw depth, validity and reserved data from one surface. Invalid, off-screen or disoccluded history has zero weight; multiplying undefined history by zero is not rejection. Sample age lives in the alpha of the `RGBA16F` history. Current eye depth is never compared with previous-camera eye depth.
- Sharpening never feeds history. Temporal blending is linear RGB. Output sharpening scales RGB together; a YCoCg Y offset that adds a constant to RGB is not that operation. `TemporalJitter` has super-resolution consumers.
- Native renderer-list draws use `unity_MatrixPreviousM` and skinned previous positions. The pipeline keeps no second native pose history, sets no per-renderer property blocks and never substitutes another camera's latest object pose.
- Encoded targets never alias `PostProcessBuffer` or `DisplayColorBuffer`. A later output draw encodes an already composed buffer and does not grade again. Read-only post bypass may alias its source. An overlay writer requires its own target.
- The backbuffer enters only through `ImportBackbuffer`; `RTHandle.SetTexture` is internal to Core RP; rebinding reallocates when the identifier changes. `ReactiveMask` has no standalone clear dispatch.
- Display-depth upsampling exists only for recorded Editor overlays that need it. `TAAConfidenceBuffer` is created only when `debugView != None` or this frame's capture requests confidence. Capture changes neither debug view nor history.
- Explicit Unity camera targets are imported by identifier.

## 14. Editor and capture

Editor windows, inspectors and debugger panels are specified in [Docs~/Manual/editor.md](Docs~/Manual/editor.md) and [Docs~/Manual/rendering-debugger.md](Docs~/Manual/rendering-debugger.md). They use Unity Editor IMGUI and Editor styles, plus one UI Toolkit drawer for the default Volume profile. The package does not define a visual design system.

Diagnostics exist only in Editor and Development builds: capture, the Rendering Debugger integration (`InfinityDebugDisplaySettings`, `EDebugView` and the per-camera debug view, panel counters, pass timings, the mesh backend override) and the debug kernels of SSR, SSGI and TAA. The static check `diagnostics` rejects their symbols outside `#if UNITY_EDITOR || DEVELOPMENT_BUILD`; A release build keeps only two inputs whose shape is fixed elsewhere, at constant values: `OutputPlan.debugOutput` (false) and the `SSRParameters.debugMode` record field (0). The pipeline reaches them only through `PipelineDiagnostics`, outside the measured frame scope: validation scenarios register `PipelineFrameObserver`s on load, the render graph exposes one `IRGExecutionObserver` slot, and normal-frame capture runs at a fixed place in that dispatcher. Diagnostic components (`LivenessMarker`, `TemporalValidationCamera`, `CameraMovement`) keep their classes and serialized fields in every build, with their behavior compiled only for diagnostics. `RenderCaptureService` records normal-frame copies through graph transfers into session-owned staging. The evidence, producer, recorded and submission frames are the `FrameContext` frame. `completionFrame` is `Time.frameCount` when the readback callback runs; that clock is not the recorded frame. A beauty capture fails when `CameraSetup.debugView` is not `None`. `RenderCaptureRequest.allowDebugView` records that view on the frame evidence and leaves the post buffer as the post output. It does not replace `camera.targetTexture` and does not call `Camera.Render`. Capture selects an explicit Game camera, or the single active Game camera. Identical screenshots of a Game view that is not redrawing are not liveness evidence: use Play mode or a differing pair. Lighting is captured from `sceneColor.opaque` before the translucent passes draw into the scene color. Debug view and history are left unchanged.

Automated Editor commands use the CLI adapter under `Editor/Cli`; its safety rules and the capture rules are in AGENTS §5. Capture does not query a retired semantic name at frame end.

## 15. Integration boundary

The ownership audit is [Docs~/Project/Audit/UnityIntegrationAudit.md](Docs~/Project/Audit/UnityIntegrationAudit.md). The rules that follow are the architectural boundary.

Native renderer content uses Unity culling and renderer lists. Custom mesh content uses `MeshWorld`. Ray tracing adapts native geometry through the public explicit-instance API of Unified Ray Tracing. Native renderer identity and custom draw generation are different. A mesh asset is not an instance identity. Native scene changes do not wait for a mesh-world revision.

Adaptive Probe Volumes are bound with Core RP's `ProbeReferenceVolume` APIs on the pipeline command buffer before the graph records. One integration owns initialization and cleanup. A material samples probes in world space. The pipeline does not upload a per-instance probe record for mesh content.

Shader Graph access is confined to `Editor/ShaderGraph/`. Runtime code does not reference Shader Graph internals. No other assembly uses an asmref, reflection into Unity internals, or a spoofed friend name for this purpose.

Custom VFX Graph outputs are unsupported. Particle systems use the translucent renderer list.

### Contracts

- Shader Graph 17.6 keeps `Target` and `SubTarget` internal. The Infinity target compiles into `Unity.ShaderGraph.Editor` through the single asmref at `Editor/ShaderGraph/` and references Infinity by strings, which `static_check.py` checks. Runtime does not depend on it.
- Adaptive Probe Volumes are bound with `ProbeReferenceVolume.BindAPVRuntimeResources` and `UpdateShaderVariablesProbeVolumes` before the graph records; no graph encoder exposes a `CommandBuffer` for that bind. Enable and disable of an entity each pair with one unregister, including disable followed by destroy.
- Native renderer content keeps lightmaps, legacy probes, light-probe proxy volumes, shadowmask and motion on Unity renderer lists. `MeshComponent` never discovers or changes a renderer and stores no lightmap or CPU per-instance probe data.
- Additional-data components own only Infinity extensions. `ObjectFactory.componentWasAdded` adds them with Undo when a native camera or light is created, and the camera inspector prepares its data. The light inspector binds native settings, including color temperature, to `Light` and reads missing or unauthored extension data without changing it. An explicit Infinity edit adds or authors only the affected lights with Undo. The new data preserves a bare light's distance and shadow-filter behavior. Each staged Infinity value change uses its own Undo group, including separate drag events. Editor load, reload and scene save do not regenerate hidden data. Terrain sector regeneration is an explicit inspector action with Undo and prefab tracking.
- Unified Ray Tracing's explicit-instance API is wrapped by an isolated adapter; its persistent-scene scope is transient and released with the adapter. Valid hardware ray-tracing assets that are not yet integrated are kept.
- `SupportedRenderingFeatures.active.rendersUIOverlay` is true. Custom VFX Graph outputs stay unsupported: no friend-assembly shim and no Package Cache patch.

## 16. Limits present in the source

These are properties of the current implementation that no subsystem section states, not a verification record. [Docs~/Project/Status/FeatureStatus.md](Docs~/Project/Status/FeatureStatus.md) states what has actually been executed. None of them is hidden behind a fallback, a disabled pass or a dummy resource.

- The material conversion wizard reports the maps InfinityLit does not expose.
- Shader Graph scene depth is available in decal graphs, scene color in T1, and the fog node returns no fog. Graph motion is rigid. Shader Graph materials have no mesh-instancing path, so `MeshComponent` does not draw them.
- `MeshComponent` Receive Shadow and Affect Indirect Lighting are stored on the entity, and no pass reads them.
- A view read by both backends is evaluated on both sides: under the default policy the main view's entities are tested once by the GPU producer and once by the CPU job for T0, T1 and T2. The CPU side tests no occluder, so under CPU Direct an occluded view draws instances the GPU side would have culled; depth hides them, and only the draw count differs.
- The light and reflection-probe complexity views count clustered-loop visits, not lights that shade the pixel.
- Unity Prefab Overrides can apply or revert the native Light and additional light data independently; a partial shape override can leave the native carrier out of sync with the authored shape.
- Light editor transaction rollback uses Unity's group-wide Undo API. Newer groups recorded by reentrant callbacks can be within the rollback range.
- Several recorded passes can contain no draws (`RasterDBuffer` without a DBuffer shader, `RasterLocalShadow` without local casters, `CopyHistory*` transfers). Frame Debugger may omit them. Cascade shadows still bind their target when the draw count is zero.
- Hi-Z, half-resolution geometry, lookup tables, light masks and the screen-space producers are async-eligible where the device allows. Overlap has not been measured. The graph compiler does not hoist async-eligible work ahead of its record position, so SSR and SSGI, recorded after `RasterForward`, cannot overlap the shadow window on an async device; recorded ahead of the shadows they cost Scene_Spazon about 7 ms of GPU time on a device without async compute. Hoisting belongs to the compiler once an async device measures a gain.
- Ray-traced ambient occlusion Player shader load is unverified.
- A pipeline whose capabilities record neither TAA nor super resolution still jitters a temporal camera and lets history features record: `CameraRenderPolicy.temporal` decides jitter and history, not the capabilities. Only the desktop pipeline runs today.
- `CameraFrameState` in the frame infrastructure owns the desktop pipeline's shadow and light-loop constant buffers (`ShadowUniform`, `LightLoopUniform`) and its combine-LUT cache, so every derived pipeline allocates them per camera; per-camera state of a derived pipeline has no slot of its own yet. `pipelinebase` lists these as the allowed exceptions.
- Combine LUT writes Rec.709 linear and dispatches only when the grading key changes. The key holds only film and grading parameters: no output setting reaches the LUT shader.
- Image-regression baselines are per graphics API, not per GPU vendor, and are absent until recorded on a verified Editor.
- Validation scenes for decals, local lights and translucency have shown sky bands, dark triangles and cube blotches. The cause is not established.
- With the Scene view and the Game view both rendering, `infinity_cpu_markers_start` counts managed allocations inside whichever marker is on the stack. The 2026-11-18 Scene_Spazon probe, Release, warmup 120, sample 30, recorded Game 1 and SceneView 7 allocations per call on GPU Indirect, camera still and moving, and Game 71 and SceneView 7 on CPU Direct. Every stack is `ProfilerSession::EnablePlaymode` → `ScriptingProfiler::WalkScriptingMetaData` → `mono_string_new`, or `NativeInputSystem.NotifyBeforeUpdate`. A Game-only probe's steady windows are 0, and `nativeSubmitAllocations` is 0. The longer CPU record covers more of the same profiler walk, which is why its Game count is higher. `EmitWorldGeometryForSceneView`, `CreateGizmoRendererList`, `CreateWireOverlayRendererList` and `Handles.ShouldRenderGizmos` remain Editor calls on the Scene-view path; they are not the owners of these bytes.
